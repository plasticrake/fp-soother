# AGENTS.md

## fp-soother-lib: BLE protocol and crypto core

- `constants.py`: characteristic UUIDs and the bit-layout tables (`STATE_ATTRS`, `AUX_ATTRS`, `INFRA_ATTRS`) that map logical field names to byte/bit offsets.
- `key_tables.py`: key material (`PAIRING_KEYS`, `KEY_REQUEST_KEYS`, `KEY_REQUEST_TABLES`, `SHARED_ENCRYPTION_KEY`).
- `encryption.py`: the SmartConnect crypto. AES-128-CBC, zero IV, no padding, and every message is exactly one 16-byte block. It also owns the two non-obvious correctness steps every read/write must go through:
  - `is_valid_state_decrypt()`: a decrypted block is only genuine if `raw[10] == raw[15] ^ raw[4]` (unique-key layout; see Protocol notes for the shared-key one). Retry reads until this passes, because the device briefly returns stale ciphertext after pairing/key exchange.
  - `descramble_decrypted_state()`: a byte permutation the firmware applies, which must run before interpreting `STATE_ATTRS`/`AUX_ATTRS` offsets.
- `protocol.py`: `SootherState` dataclass plus bit-level encode/decode (`decode_state`, `decode_aux_state`, `decode_infra_state`) and command-frame builders (`build_state_command`, `build_rtc_update_command`, `build_custom_color_sequence_command`, `build_preset_command`), all framed by `frame_command()`.
- `pairing.py`: the pairing handshake. Read `CHAR_INFRA_STATE` → derive shared pairing key → decrypt `CHAR_STATE` to get `changeCmdAuthKey` → send a key-request on `CHAR_INFRA_UPDATE` → decrypt the reply into a session key → send a required `rtcUpdate` command (the firmware waits for this specific command before leaving pairing mode).
- `client.py`: `SootherClient`, the high-level async API. `open()`/`close()` support long-lived callers (e.g. the web `DeviceManager`); `connect()` is an async context manager for scoped use. See below for the `_io_lock` read-modify-write serialization and the `establish_connection()`/`BLEDevice` resolution details.
- `scanner.py`: BLE discovery (`scan`, `find_soother`) and `dump_gatt` for exploring an unknown device's GATT table.

`CHAR_AUX_STATE` is not plaintext despite its own `AUX_ATTRS` table; see the detailed note below and `SootherClient._read_raw_aux_state()`. `CHAR_INFRA_STATE` (firmware version/error) is plaintext.

## Protocol notes

- The library has two crypto modes. `SootherClient._detect_crypto_mode()` picks one per device on every connect from `CHAR_INFRA_STATE`'s plaintext `firmwareVersion`, the same way the real app does (`dyw47.json` `encryption_methods`: `uniqueKey.minimumFirmwareVersion = 9`, mirrored as `constants.UNIQUE_KEY_MIN_FIRMWARE_VERSION`).
  - Unique-key (firmware >= 9): per-device session key from `pairing.pair()`; checksum `raw[10] == raw[15] ^ raw[4]`, `RAW_TO_STATE_MAP`, changeCmdAuthKey `raw[6], raw[15], raw[4]`.
  - Shared-key (firmware < 9): static `key_tables.SHARED_ENCRYPTION_KEY` and no key exchange at all (`pair()` just sends `rtcUpdate`); checksum `raw[3] == raw[5] ^ raw[6]`, `SHARED_KEY_RAW_TO_STATE_MAP`, changeCmdAuthKey `raw[0], raw[6], raw[5]`; command frames use `protocol.frame_command()`'s shared-key layout. The key is the native `getEncryptionKey()` slot 17 (not the device's legacy type 11) with the usual `+i` ramp salt, and it equals `PAIRING_KEYS[19]`. Both layouts come from the arm64 disassembly of the native decrypt/encrypt cores (`SmartCrypto_v2.bin` at `0x7900`/`0x7c18`; the mode flag is the per-key byte at `ctx+0x210`). They were confirmed live against a firmware-8 dyw47: state reads, aux reads, notifications, and nightlight/volume/rtcUpdate writes.
  - A `shared_key: bool` keyword on `encryption`'s checksum/descramble helpers and on every `build_*_command()` selects the layout. The default (`False`) is the unique-key layout. Every builder produces a logical payload (`pt[0]` = command id, then value bytes) that `frame_command()` scrambles.
- A firmware-8 device was observed to stop advertising for a while after each disconnect, so back-to-back standalone connects (e.g. consecutive CLI invocations) can fail with "Could not find a BLE device advertising". Long-lived connections are unaffected.
- `CHAR_AUX_STATE` (E2BCFFF8, backing `captive_sleep_stage_timer`/`soothe_sleep_stage_timer`/`sleep_stage_timer`) is not a bare plaintext buffer, despite its own `AUX_ATTRS` bit-layout table in `constants.py`. On the wire it is framed identically to `CHAR_STATE`: a 16-byte AES-128-CBC block (same session key) that must pass the same checksum and go through the same `descramble_decrypted_state()` byte permutation before `AUX_ATTRS`' byte/bit offsets apply. Treating it as plaintext decodes near-random noise into all three sleep-stage fields on every read, since AES-CBC's avalanche effect makes unrelated fields appear to change together. Confirmed live: decoding a freshly set field through the decrypt, checksum and descramble steps reproduces the exact value just written. See `SootherClient._read_raw_aux_state()`. `CHAR_INFRA_STATE` (firmware version/error) is plaintext and unaffected.
- `SootherClient` serializes all BLE reads/writes for a device behind a single `asyncio.Lock` (`_io_lock`). Every command is read-modify-write: rolling anti-replay tokens come from the most recent raw state, and a fresh state is re-read afterward. Without serialization, two commands issued close together (e.g. two UI controls changed in quick succession) can interleave and corrupt each other's rolling tokens or read a mid-transition state. Internal methods already holding the lock must call `_refresh_state_locked()`, not the public `refresh_state()`, to avoid deadlock (`asyncio.Lock` is not reentrant).
- `SootherClient` (and `pairing.pair()`) connect via `bleak_retry_connector.establish_connection()`, not a raw `BleakClient(address).connect()`. Host Bluetooth managers (e.g. Home Assistant) hand integrations an already-resolved `BLEDevice` and expect retry/timeout handling to go through it. `establish_connection()` requires a `BLEDevice`, not a bare address string, so `SootherClient._resolve_ble_device()` obtains one on every connect attempt. A caller-supplied `ble_device_callback` takes precedence and is re-invoked each time, so a host can hand us its current best route to the device on every reconnect. Next comes a caller-supplied fixed `ble_device`. Only if neither is given do we fall back to our own `BleakScanner.find_device_by_address()` lookup, which is the default for plain string-address CLI/web use. Standalone connects therefore do a brief scan first, so the device must be advertising. A host that owns the sole system-wide `BleakScanner` (e.g. Home Assistant) must never call `find_soother()`/`scan()`/`SootherClient.discover()`, because they instantiate their own `BleakScanner`. It should resolve and track devices with its own scanner API and pass the result to `SootherClient` as `ble_device`/`ble_device_callback`. Because `establish_connection()`'s own `max_attempts` retries can make a full failed-connect sequence take noticeably longer than a single attempt, "schedule BLE connects as background tasks" (see `fp-soother-web`'s `AGENTS.md`) matters even more.
- `CMD_PRESET` (22) is a composite command that bundles every settable attribute into one 16-byte write (`build_preset_command()` in `protocol.py`, `PRESET_ATTRS`/`PRESET_BYTE_LENGTH` in `constants.py`, `SootherClient.send_preset(**overrides)`), matching the real app's "apply a favorite" behavior instead of one write per attribute. `PRESET_ATTRS` is direct evidence (`dyw47.json`'s `"presets"` section). The byte layout of the final 16-byte frame, meaning how the packed 8-byte preset payload combines with the changeCmdAuthKey-derived rolling tokens, comes from the decompiled app rather than a live capture.
