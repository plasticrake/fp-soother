# AGENTS.md

## fp-soother-lib — BLE protocol and crypto core

- `constants.py` — characteristic UUIDs and the bit-layout tables (`STATE_ATTRS`, `AUX_ATTRS`, `INFRA_ATTRS`) that map logical field names to byte/bit offsets.
- `key_tables.py` — (`PAIRING_KEYS`, `KEY_REQUEST_KEYS`, `KEY_REQUEST_TABLES`).
- `encryption.py` — the SmartConnect crypto: AES-128-CBC, zero IV, no padding, every message exactly one 16-byte block. Also owns the two non-obvious correctness steps every read/write must go through:
  - `is_valid_state_decrypt()` — a decrypted block is only genuine if `raw[10] == raw[15] ^ raw[4]`; retry reads until this passes (the device briefly returns stale ciphertext after pairing/key exchange).
  - `descramble_decrypted_state()` — a byte permutation the firmware applies that must run before interpreting `STATE_ATTRS`/`AUX_ATTRS` offsets.
- `protocol.py` — `SootherState` dataclass plus bit-level encode/decode (`decode_state`, `decode_aux_state`, `decode_infra_state`) and command-frame builders (`build_state_command`, `build_rtc_update_command`, `build_custom_color_sequence_command`).
- `pairing.py` — the pairing handshake: read `CHAR_INFRA_STATE` → derive shared pairing key → decrypt `CHAR_STATE` to get `changeCmdAuthKey` → send a key-request on `CHAR_INFRA_UPDATE` → decrypt the reply into a session key → send a required `rtcUpdate` command (the firmware specifically waits for this before leaving pairing mode).
- `client.py` — `SootherClient`, the high-level async API. `open()`/`close()` support long-lived callers (e.g. the web `DeviceManager`); `connect()` is an async context manager for scoped use. See below for the `_io_lock` read-modify-write serialization and the `establish_connection()`/`BLEDevice` resolution details.
- `scanner.py` — BLE discovery (`scan`, `find_soother`) and `dump_gatt` for exploring an unknown device's GATT table.

`CHAR_AUX_STATE` is not plaintext despite its own `AUX_ATTRS` table — see the detailed note below and `SootherClient._read_raw_aux_state()`. `CHAR_INFRA_STATE` (firmware version/error) is genuinely plaintext.

## Protocol notes

- `CHAR_AUX_STATE` (E2BCFFF8, backing `captive_sleep_stage_timer`/`soothe_sleep_stage_timer`/`sleep_stage_timer`) is NOT a bare plaintext buffer despite its own `AUX_ATTRS` bit-layout table in `constants.py`. On the wire it is framed identically to `CHAR_STATE`: a 16-byte AES-128-CBC block (same session key) that must pass the same `raw[10] == raw[15] ^ raw[4]` checksum and go through the same `descramble_decrypted_state()` byte permutation before `AUX_ATTRS`' byte/bit offsets apply. Treating it as plaintext (the original implementation) decodes near-random noise into all three sleep-stage fields on every read, since AES-CBC's avalanche effect makes unrelated fields appear to change together -- confirmed live: decoding a freshly-set field through the proper decrypt+checksum+descramble pipeline reproduces the exact value just written. See `SootherClient._read_raw_aux_state()`. `CHAR_INFRA_STATE` (firmware version/error) is genuinely plaintext and unaffected.
- `SootherClient` serializes all BLE reads/writes for a device behind a single `asyncio.Lock` (`_io_lock`). Every command is read-modify-write (rolling anti-replay tokens drawn from the most recent raw state, then a fresh state re-read afterward); without serialization, two commands issued close together (e.g. two UI controls changed in quick succession) can interleave and corrupt each other's rolling tokens or read a mid-transition state. Internal methods already holding the lock must call `_refresh_state_locked()`, not the public `refresh_state()`, to avoid deadlock (`asyncio.Lock` is not reentrant).
- `SootherClient` (and `pairing.pair()`) connect via `bleak_retry_connector.establish_connection()`, not a raw `BleakClient(address).connect()` -- this is required for compatibility with host Bluetooth managers (e.g. Home Assistant) that hand integrations an already-resolved `BLEDevice` and expect retry/timeout handling to go through it. `establish_connection()` requires a `BLEDevice`, not a bare address string, so `SootherClient._resolve_ble_device()` obtains one on every connect attempt: a caller-supplied `ble_device_callback` (re-invoked fresh each time, so a host can hand us its current-best route to the device on every reconnect) takes precedence, then a caller-supplied fixed `ble_device`, and only if neither is given do we fall back to our own `BleakScanner.find_device_by_address()` lookup -- the default for today's plain string-address CLI/web use. This is a deliberate behavior change from the old direct connect-by-address: standalone connects now do a brief scan first, so the device must be advertising. A host that owns the sole system-wide `BleakScanner` (e.g. Home Assistant) must never call `find_soother()`/`scan()`/`SootherClient.discover()` (they instantiate their own `BleakScanner`) -- it should resolve/track devices via its own scanner API and pass the result to `SootherClient` as `ble_device`/`ble_device_callback` instead. Because `establish_connection()`'s own `max_attempts` retries can make a full failed-connect sequence take noticeably longer than a single attempt, "schedule BLE connects as background tasks" (see `fp-soother-web`'s `AGENTS.md`) is more important, not less.
- `CMD_PRESET` (22) is a composite command bundling every settable attribute into one 16-byte write (`build_preset_command()` in `protocol.py`, `PRESET_ATTRS`/`PRESET_BYTE_LENGTH` in `constants.py`, `SootherClient.send_preset(**overrides)`), matching the real app's "apply a favorite" behavior instead of one write per attribute. `PRESET_ATTRS` is direct evidence (`dyw47.json`'s `"presets"` section), but the byte layout of the final 16-byte frame -- how the packed 8-byte preset payload combines with the changeCmdAuthKey-derived rolling tokens.
